### 로그 수집 전송

- 기능 설명: 게임 로그와 Unity 콘솔 로그를 세션 단위 JSONL 파일로 기록하고, 프로그램 종료 시 gzip으로 압축해 로그 서버로 전송한다. 전송에 실패한 파일은 pending으로 보존해 다음 기동 때 재전송한다.
- 동작 조건 및 처리 흐름: RuntimeInitializeOnLoadMethod에서 GameLogger 싱글턴이 생성되고 logMessageReceivedThreaded로 콘솔 로그를 수집한다. 큐의 항목은 5초마다 persistentDataPath/Logs/{세션ID}.jsonl에 추가된다. 종료 시 wantsToQuit(플레이어)와 OnApplicationQuit(에디터 포함)에서 큐를 비우고 파일을 UploadBatch로 조립해 포그라운드 스레드에서 동기 HTTP로 전송한다. 서버 2xx 응답이면 파일을 삭제하고 실패하면 .pending으로 바꾼다. 다음 기동에서 남은 파일과 pending 파일을 endedCleanly=false로 재전송한다.
- 구현 상태: 유니티 클라이언트와 서버 수신기·처리기 구현 완료. 서버는 curl 기반 6항목 검증 통과. 유니티 실연동(Play 종료 전송), 빌드 동작, 강제종료 재전송은 미확인.

#### 연결 및 협업

- 연결된 기능: 없음(독립 기능). 서버 측 수신기·처리기 계약은 docs/plans/로그_수집_전송_구현계획.md 3장과 5장을 따르며 서버가 구현됐다.
- 공유하는 코드 및 상태: MonoSingleton의 CurrentInstance와 _quitting 규약을 사용한다. persistentDataPath/Logs 폴더에 세션 파일을 만들며 유니티 기본 Player.log와는 별개다. 클라이언트와 서버는 JSON 키, ApiKey(dev-log-key), 주소(포트 5000 /api/logs)를 공유한다.
- 중복 또는 충돌 사항: 없음.
- 승인 필요 사항 및 결과: 서버 주소는 Inspector의 개발용·릴리즈용 두 필드로 분리하고 빌드 유형에 따라 자동 선택하도록 확정했다. 서버 측 판단 사항(data/raw 경로, /api/summary API 키 필수, sessionId 정규식, Assert를 errors에 합산)은 구현계획 문서에 기록하고 승인했다.

#### 검증 결과

- dotnet build Assembly-CSharp.csproj: 오류 0개. 경고 12건은 모두 기존 항목(참조 버전 MSB3277, KatanaV2 CS0649·CS0414)이고 새 코드 경고는 없다.
- LogServer: dotnet build 경고 0·오류 0. curl 기반 6항목 검증 통과(202 신규·200 replaced 멱등, 401·413·400 오류 경로, 요약 upsert, BOM·RFC 4180 왕복, sessionId 경로탈출 400, raw 만료 정리).
- 계약 일치 확인: Unity UploadBatch·LogEntry JSON 키와 서버 Dto camelCase 매칭, ApiKey·포트·경로 일치, sessionId 정규식과 유니티 세션 ID 형식 호환.
- 미확인: 유니티 클라이언트 실연동 전송(Play 종료), 빌드 후 동작, 강제종료 후 재전송. 계획 문서 9장 수동 검증 체크리스트로 6단계에서 확인한다.
- 구현 비고: 설계의 StreamWriter 유지 방식 대신 배치마다 File.AppendAllText로 열고 닫는 방식을 채택했다. 크래시 시 열린 핸들 손실 위험을 없애고 파일 상태 전환이 단순해진다.
