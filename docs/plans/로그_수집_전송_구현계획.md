# 로그 수집·전송 시스템 구현 계획 (자체 구현 파이프라인)

- 작성일: 2026-10-13
- 현재 상태: 1~4단계 완료(서버는 curl 기반 검증). 5단계(선택)와 6단계(유니티↔서버 실연동 통합 검증) 남음
- 다음 작업: 6단계 통합 검증 또는 5단계 선택 구현
- 작성 근거: 사용자가 프로그램 종료 시 유니티 로그를 서버로 전송하고, 서버가 CSV/Google Sheets로 저장하는 기능을 요청했다. 여러 방법을 비교한 결과 자체 구현 파이프라인(추천안 1)이 채택됐다.
- 이 문서는 실행된 기능명세가 아니라 향후 작업 계획이다. 각 단계 구현 후 docs/FEATURE_SPEC.md와 기능명세에 실제 변경과 검증 결과를 반영한다.

## 1. 목표와 범위

- 유니티 클라이언트의 모든 로그(Debug.Log 계열 자동 캡처 + 전투 등 구조화 로그)를 로컬 파일에 기록한다.
- 프로그램 종료 시 로그를 서버로 전송한다. 전송 실패 시 다음 실행 때 재전송한다.
- 서버는 로그를 수신해 세션별 CSV로 저장하고, 세션 요약을 월별 요약 CSV로 집계한다.
- 선택 사항으로 월별 요약 CSV를 Google Sheets에 올린다.
- 대상 플랫폼은 Windows 스탠드얼론(에디터 포함)이다. WebGL은 스레드·동기 HTTP 제약으로 범위에서 제외한다.
- Prometheus는 이 계획에 포함하지 않는다. 세션 정량 지표 대시보드가 필요해지면 확장으로 추가한다.

## 2. 전체 아키텍처

```
[Unity 클라이언트]                                [서버 (LogServer)]
GameLogger(수집)                                    POST /api/logs (수신기)
  ├─ Application.logMessageReceivedThreaded ──┐          │ 검증·역압축·역직렬화
  ├─ 구조화 로그 API(Info/Warn/Error/Combat) ──┤          ▼
  ▼                                          │    처리기 파이프라인
LogFileWriter(로컬 JSONL 버퍼)                 │          ├─ 정규화·CSV 이스케이프
  persistentDataPath/Logs/{세션ID}.jsonl      │          ├─ data/sessions/{세션ID}.csv 교체 기록
  ▼                                          │          └─ data/summary/{yyyy-MM}.csv upsert
LogUploader(전송기)                           │
  ├─ 기동 시: 미전송(.pending) 파일 재전송 ────┘
  ├─ 종료 시: 현재 세션 파일 gzip → HTTP POST
  └─ 실패 시: 파일을 .pending으로 유지
                                               선택: tools/sheets_export(스크립트)
                                                 data/summary/{yyyy-MM}.csv → Google Sheets 탭
```

## 3. 데이터 계약

### 3.1 로그 항목 (Unity `LogEntry`)

JsonUtility 호환을 위해 모든 필드는 flat 문자열·숫자로 유지한다. 구조화 데이터는 호출자가 직렬화한 JSON 문자열 하나(`dataJson`)로 담는다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `timestampUtc` | string | UTC ISO 8601 ("o" 포맷) |
| `level` | string | `Info` / `Warning` / `Error` / `Assert` / `Exception` |
| `category` | string | `Unity`(자동 캡처) 또는 호출자 지정(`Combat`, `System` 등) |
| `scene` | string | 기록 시점 활성 씬 이름 |
| `message` | string | 로그 본문 |
| `dataJson` | string | 구조화 부가 데이터(JSON) 또는 빈 문자열 |
| `stackTrace` | string | 자동 캡처 시 유니티 제공 스택트레이스, Error 이상 수동 호출 시 `Environment.StackTrace` |

### 3.2 세션 헤더 (Unity `LogSessionHeader`)

세션 JSONL 파일의 첫 줄. 크래시 후 재시작 시에도 메타데이터를 복원하기 위해 파일에 함께 기록한다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `sessionId` | string | 기동 시 생성. GUID 앞 8자리 + 시작 시각 접미 (예: `a1b2c3d4_20261013_091522`) |
| `startedAtUtc` | string | 세션 시작 시각 |
| `appVersion` | string | `Application.version` |
| `unityVersion` | string | `Application.unityVersion` |
| `isEditor` | bool | 에디터 실행 여부 |
| `platform` | string | `Application.platform` |

### 3.3 업로드 봉투 (Unity·서버 공용 `UploadBatch`)

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| 헤더 6종 | 위와 동일 | LogSessionHeader 필드를 평면으로 펼쳐 담는다 |
| `endedAtUtc` | string | 전송 시점 종료 시각. 정상 종료면 flush 시각, 재시작 재전송이면 파일의 마지막 항목 시각 |
| `endedCleanly` | bool | 정상 종료 경로에서 전송되면 true, 재시작 재전송이면 false |
| `truncated` | bool | 캡처 상한 초과로 일부 로그를 버렸으면 true |
| `entries` | LogEntry[] | 세션 전체 로그. 상한 20,000건 |

### 3.4 API 계약

```
POST /api/logs
Headers:
  Content-Type: application/json
  Content-Encoding: gzip
  X-Api-Key: {서버가 발급한 키}
Body: UploadBatch를 gzip 압축한 JSON

응답 202 { "sessionId": "...", "accepted": 1234 }          신규 저장
응답 200 { "sessionId": "...", "accepted": 1234, "replaced": true }  동일 세션 재전송(교체)
응답 401 API 키 불일치 / 413 크기 초과 / 400 파싱 실패
GET /health → 200 "ok"
GET /api/summary/{yyyy-MM}.csv → 요약 CSV 내려받기(보조 기능)
```

- 멱등성: 같은 `sessionId` 재전송 시 서버는 해당 세션 CSV를 통째로 교체한다. 재시도로 중복 행이 생기지 않는다.
- 단일 배치 설계: 세션 전체를 한 번에 보낸다. 클라이언트가 세션당 캡처를 20,000건으로 제한하고 초과분은 버리고 `truncated`를 남긴다. 분할 전송의 순서·조립 복잡도를 피한다.

### 3.5 CSV 스키마

세션 원본 `data/sessions/{sessionId}.csv` (UTF-8 with BOM, RFC 4180 이스케이프 — Excel 한글 호환):

```
timestamp_utc, level, category, scene, message, data_json, stack_trace
```

세션 요약 `data/summary/{yyyy-MM}.csv` (세션ID 키 upsert):

```
session_id, date_utc, duration_sec, ended_cleanly, total, warnings, errors, exceptions, is_editor, platform, app_version
```

- `duration_sec`: endedAtUtc − startedAtUtc (초, 소수 1자리).
- 요약은 원본 세션 CSV를 다시 읽어 계산하지 않고, 수신 시 메모리에서 집계해 바로 기록한다.

## 4. Unity 측 설계

### 4.1 클래스 구성과 파일 위치

| 파일 | 클래스 | 역할 |
| --- | --- | --- |
| `Assets/Scripts/Logging/GameLogger.cs` | GameLogger : MonoSingleton<GameLogger> | 로그 클래스. 수집·버퍼링·전송 지휘 |
| `Assets/Scripts/Logging/LogModels.cs` | LogEntry, LogSessionHeader, UploadBatch | 직렬화 모델 ([Serializable]) |
| `Assets/Scripts/Logging/LogFileWriter.cs` | LogFileWriter | 로컬 JSONL 파일 입출력 (plain class) |
| `Assets/Scripts/Logging/LogUploader.cs` | LogUploader | 배치 조립·gzip·HTTP 전송 (plain class) |

- Managers 서비스로 넣지 않고 독립 싱글턴으로 둔다. 이유: 부팅 첫 프레임부터 로그를 캡처해야 하고, Managers 정리 이후에도 종료 flush가 동작해야 하며, 로그 시스템 실패가 게임을 죽이면 안 된다.
- 부트스트랩: `[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.AfterSceneLoad)]`에서 `GameLogger.Init()`을 호출한다. MonoSingleton은 Play 모드에서만 생성 가능하므로 이 시점은 Play 모드 진입 후라 안전하다.
- GameLogger의 정적 API는 인스턴스가 없으면 예외를 던지지 않고 조용히 무시한다. 로깅이 게임을 절대 중단시키지 않는다.

### 4.2 GameLogger (로그 클래스)

역할별 공개 API:

```csharp
// 자동 캡처: Debug.Log/Warning/Error/Assert/Exception 전부
void OnLogMessageReceived(string condition, string stackTrace, LogType type)

// 구조화 로그 (호출자용)
public static void Info(string category, string message)
public static void Warn(string category, string message)
public static void Error(string category, string message)
public static void Data(string level, string category, string message, object data)  // data는 JsonUtility로 직렬화

// 수명 주기
public static void Init()          // RuntimeInitializeOnLoadMethod에서 호출
protected override void InitializeSingleton()
void OnEnable()  /  void OnDisable()   // logMessageReceivedThreaded 구독·해제
void Update()                        // 주기 flush 타이머
protected override void OnApplicationQuit()   // base 호출 후 flush 트리거
```

- 내부 큐: `Queue<LogEntry>` + lock. `Update`에서 큐가 비면 파일 스트림을 닫아 리소스를 회수한다.
- 스택트레이스: Error 이상 수동 호출에서만 `Environment.StackTrace`를 남긴다. Info 수동 호출은 비용을 피해 생략.
- 캡처 상한: 세션당 20,000건. 초과 시 큐에 넣지 않고 `truncated` 플래그만 세운다. 상한 도달 사실 자체를 마커 항목으로 한 번 기록한다.

### 4.3 LogFileWriter (로컬 버퍼)

- 파일: `Application.persistentDataPath/Logs/{sessionId}.jsonl`. 첫 줄은 LogSessionHeader JSON, 이후 줄은 LogEntry JSON.
- 쓰기 정책: lock 걸고 `File.AppendAllText`로 배치 append, 이후 `Update` 타이머(기본 5초) 또는 64건 모임 때 닫았다가 재오픈하지 않고 StreamWriter 유지 + Flush. 크래시 안전이 우선이므로 AutoFlush를 켠다.
- pending 규약: 전송 실패한 파일은 `{sessionId}.jsonl.pending`으로 이름을 바꿔 보존한다. 전송 성공 시 파일을 삭제한다.
- 정리: 기동 시 30일 지난 pending 파일은 삭제한다.

### 4.4 LogUploader (전송기)

- 전송 스레드: `Thread` 하나에서 동기 `HttpWebRequest`를 사용한다(`GetResponse`, 타임아웃 5초). UnityWebRequest는 비동기라 종료 도중 보장이 없어 쓰지 않는다.
- 배치 조립: 파일의 헤더 줄과 엔트리 줄을 각각 `JsonUtility.FromJson`으로 읽어 UploadBatch를 만든다. `endedCleanly`는 호출 시점 문맥으로 세운다.
- 압축: `GZipStream(System.IO.Compression)`으로 직렬화 결과를 압축해 본문으로 쓴다.
- 재시도: 전송 스레드 안에서 2회(즉시 1회 재시도). 그래도 실패하면 파일을 `.pending`으로 유지하고 다음 기동 때 다시 시도한다.
- 기동 재전송: `Init`에서 pending 파일을 찾아 백그라운드로 전송한다(본 세션 기록과 독립).

### 4.5 종료 시퀀스

1. `Application.wantsToQuit` 구독(OnEnable에서): 핸들러에서 flush 스레드를 시작하고 최대 3초간 `Thread.Join(timeout)`으로 대기한 뒤 true를 반환해 종료를 막지 않는다.
2. `OnApplicationQuit`(MonoSingleton override, base 호출): wantsToQuit이 불린 경로가 아닐 때의 이중 안전장치. 1초 한도로 재시도.
3. `OnDisable`: 네트워크 시도 없이 파일 스트림만 닫는다.
4. 에디터: Play 종료는 위 경로와 동일하게 동작한다. 에디터 앱 자체 종료는 `#if UNITY_EDITOR`로 `EditorApplication.quitting`에도 같은 flush를 연결한다.

- 어떤 경로에서도 최악의 결과는 "로컬 파일에만 남고 다음 실행 때 전송"이다. 무손실 목표를 종료 전송이 아니라 파일+재전송이 담당한다.

### 4.6 Inspector 설정값 ([SerializeField] private)

| 필드 | 기본값 | 설명 |
| --- | --- | --- |
| `_serverUrl` | `http://localhost:5000/api/logs` | 수신 엔드포인트 |
| `_apiKey` | 개발용 기본값 | X-Api-Key 헤더 값 |
| `_flushIntervalSeconds` | 5 | 큐→파일 flush 주기 |
| `_uploadOnQuit` | true | 종료 시 전송 사용 여부 |
| `_retryPendingOnStartup` | true | 기동 시 pending 재전송 |
| `_captureUnityLogs` | true | Debug.Log 계열 자동 캡처 |
| `_maxEntriesPerSession` | 20000 | 캡처 상한 |
| `_requestTimeoutSeconds` | 5 | HTTP 타임아웃 |

## 5. 서버 측 설계

### 5.1 기술 선택

- ASP.NET Core 8 Minimal API (C#). 팀 언어와 통일하고, 클라 DTO 정의를 그대로 공유할 수 있다. Python 선호 시 계약(3장)은 그대로 두고 FastAPI로 대체 가능하다.
- 의존성 없는 단일 프로세스. 파일 시스템이 저장소다. DB는 쓰지 않는다.

### 5.2 프로젝트 구조 (저장소 루트에 `LogServer/`)

```
LogServer/
  LogServer.csproj
  Program.cs          엔드포인트 등록, 옵션 바인딩, 파이프라인 호출
  ApiKeyAuth.cs       X-Api-Key 검사 미들웨어
  Dto.cs              UploadBatch, LogEntry (클라와 필드 동일)
  CsvSessionStore.cs  세션 CSV 교체 기록, RFC 4180 이스케이프, BOM
  SessionSummary.cs   요약 집계 + summary/{yyyy-MM}.csv upsert
  appsettings.json    ApiKey, DataPath, MaxBodyBytes(기본 5MB)
  data/               실행 시 생성 (sessions/, summary/)
```

### 5.3 수신기

- `POST /api/logs`: 크기 검사(413) → API 키 검사(401) → gzip 해제 → 역직렬화(400) → 처리기 호출 → 202/200.
- 동일 sessionId 재수신 시 기존 세션 CSV를 교체하고 200 `replaced:true`.
- 동시성: 세션별로 파일 뮤텍스. 같은 세션 동시 업로드는 마지막 수신이 이긴다(멱등 교체라 안전).

### 5.4 처리기 (파이프라인)

1. 정규화: message 2,000자, stackTrace 8,000자, dataJson 4,000자로 절단. 개행은 `\n`으로 통일.
2. 세션 CSV 기록: `sessions/{sessionId}.csv`에 헤더 행 + 전체 행을 새로 쓴다(교체).
3. 요약 집계: 레벨별 카운트, duration, endedCleanly를 계산해 `summary/{yyyy-MM}.csv`에서 해당 sessionId 행을 교체(upsert).
4. 원본 보존 옵션: `appsettings.json`의 `KeepRawJsonl`이 true면 수신 원문을 `raw/{sessionId}.jsonl.gz`로도 저장한다(기본 true, 디스크 여유 시).

### 5.5 Google Sheets 내보내기 (선택, 서버 프로세스와 분리)

- `tools/sheets_export/export_summary.py` (Python + gspread, 서비스 계정 JSON 키).
- 동작: `data/summary/{yyyy-MM}.csv`를 읽어 스프레드시트의 `{yyyy-MM}` 탭을 통째로 교체한다. 원시 로그 전체가 아니라 요약 행만 올린다(셀 한도·가독성).
- 실행: 수동 또는 Windows 작업 스케줄러 매일 1회. 실패해도 서버 저장에는 영향이 없다.
- 사전 준비: Google Cloud 프로젝트에서 Sheets API 활성화, 서비스 계정 키 발급, 스프레드시트를 서비스 계정 이메일에 공유.

## 6. 장애·경계 조건

| 상황 | 동작 |
| --- | --- |
| 종료 시 서버 다운 | 클라이언트 재시도 2회 실패 후 파일을 `.pending`으로 유지 |
| 플레이 중 크래시/강제종료 | 파일이 이미 디스크에 있음. 다음 기동 재전송. `endedCleanly=false` |
| 같은 세션 재전송 | 서버가 세션 CSV 통째로 교체(멱등) |
| 로그 폭주 | 캡처 상한 20,000건 + truncated 마커 |
| 본문 과대 | 클라 gzip, 서버 5MB 상한(413). 초과분은 pending 유지 후 다음 기동 재시도 |
| 시계 불일치 | 모든 시각은 UTC ISO 8601로 통일 |
| pending 파일 무한 누적 | 30일 경과분 기동 시 삭제 |
| 로깅 자체의 예외 | GameLogger 내부 try/catch로 삼키고 게임 진행 보장 |

## 7. 보안·개인정보

- 전송은 API 키 헤더로 최소 검증한다. 실서비스 배포 시 HTTPS(리버스 프록시 또는 클라우드 종단)를 전제로 하고, 플레이테스트 LAN 운영 시엔 HTTP를 허용한다.
- 스택트레이스에 로컬 사용자명이 포함될 수 있다. 서버 보존 기간을 두고(권장: 90일 후 raw 삭제) 시트에는 요약만 올려 노출을 줄인다.
- 수집 항목에 개인정보(계정, 식별자)는 넣지 않는다. sessionId는 랜덤이며 사용자와 연결되지 않는다.

## 8. 단계별 구현 계획과 완료 기준

| 단계 | 작업 | 상태 |
| --- | --- | --- |
| 1 | Unity 로그 수집·로컬 JSONL 저장 | 구현·컴파일 확인 완료 — 서버 연동 검증은 6단계로 이월 |
| 2 | Unity 전송기(종료 flush, 기동 재전송) | 구현·컴파일 확인 완료 — 서버 연동 검증은 6단계로 이월 |
| 3 | 서버 수신기 + 세션 CSV | 구현·검증 완료 — 유니티 실연동은 6단계로 이월 |
| 4 | 세션 요약 집계 + summary CSV | 구현·검증 완료 — 유니티 실연동은 6단계로 이월 |

### 1단계 — Unity 로그 수집·로컬 JSONL 저장

- GameLogger, LogModels, LogFileWriter를 구현한다. 자동 캡처와 구조화 API, 주기 flush, 세션 파일 작성까지.
- MonoSingleton 규약(Play 모드 전용, _quitting)과 충돌하지 않게 수명 주기를 확인한다.
- 완료 기준: Play 진입~종료 사이 `{sessionId}.jsonl`이 생성되고 첫 줄 헤더 + 엔트리 줄이 기록된다. 컴파일 오류 0.
- 실행 결과(2026-10-13): 4개 클래스 구현 완료. 설계의 StreamWriter 유지 대신 배치마다 File.AppendAllText로 기록해 크래시 안전성을 높였다. dotnet build 오류 0, 새 코드 경고 0. 실제 Play 검증은 6단계로 이월한다.

### 2단계 — Unity 전송기

- LogUploader 구현: 배치 조립, gzip, HttpWebRequest 동기 전송, wantsToQuit/OnApplicationQuit flush, pending 재전송.
- 완료 기준: 로컬 HTTP 수신 대상에 종료 시 1회 POST가 나가고, 실패 시 `.pending`이 남는다. 에디터 Play 종료에서 최대 3초 내 종료가 끝난다.
- 실행 결과(2026-10-13): 구현 완료. 전송은 포그라운드 스레드 + 동기 HttpWebRequest(기본 5초 타임아웃, 종료 대기 상한 3초)로 한다. 서버 주소는 개발용·릴리즈용 Inspector 필드 두 개로 분리하고 UNITY_EDITOR·DEVELOPMENT_BUILD 전처리기로 자동 선택한다. 실제 전송 검증은 6단계로 이월한다.

### 3단계 — 서버 수신기 + 세션 CSV

- LogServer 프로젝트 생성, /api/logs와 /health, ApiKeyAuth, CsvSessionStore 구현.
- 완료 기준: 실제 업로드가 세션 CSV로 저장되고, 같은 세션 재전송 시 행이 중복되지 않고 교체된다. Excel에서 한글이 정상 표시된다(BOM).
- 실행 결과(2026-10-14): LogServer(ASP.NET Core 8 Minimal API) 구현 완료. curl 기반 검증으로 202 신규·200 replaced 멱등 교체, 401·413·400 오류 경로, BOM·RFC 4180 왕복, sessionId 경로탈출 400 확인. 세션 CSV는 임시파일 후 원자적 교체로 저장한다.

### 4단계 — 세션 요약 집계

- SessionSummary 구현, 월별 summary upsert, GET /api/summary 제공.
- 완료 기준: 세션 재전송·반복 수신에도 sessionId당 요약 행이 1행으로 유지된다.
- 실행 결과(2026-10-14): 요약 upsert 검증 완료(같은 세션 재전송 시 1행 유지, duration 초 단위 1자리 불변 문화권). 월별 파일 분리와 없는 달 404 확인.

### 5단계 — Google Sheets 내보내기(선택)

- gspread 스크립트와 서비스 계정 키 발급 안내.
- 완료 기준: 스크립트 실행 시 월 탭이 요약 CSV 내용으로 교체된다.

### 6단계 — 통합 검증 + 명세 반영

- 검증 시나리오는 9장 체크리스트. 결과를 docs/FEATURE_SPEC.md와 새 기능명세(`docs/features/로그_수집_전송.md`)에 반영한다.

## 8-1. 서버 구현 시 확정한 판단 사항 (2026-10-14 승인)

- raw 저장 위치: 문서 5.2의 raw/ 대신 data/raw/{sessionId}.jsonl.gz로 구현. 확장자는 문서 규약을 유지하지만 내용은 UploadBatch JSON 봉투다.
- GET /api/summary: 문서 미명세였던 인증을 /api 접두 경로 공통 규칙에 따라 API 키 필수로 처리. /health만 무인증.
- sessionId 검증: 계약에 없던 정규식 ^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$ 를 경로탈출 방어로 추가, 위반 400. 유니티 세션 ID 형식(a1b2c3d4_yyyyMMdd_HHmmss, 24자)과 호환 확인.
- Assert 집계: 요약 CSV에 assert 컬럼이 없어 errors에 합산. 필요 시 요약 열 확장으로 분리한다.
- gzip 해제 상한: 압축 본문만 5MB 제한. zip bomb 방어는 미포함이며 LAN 플레이테스트 가정에서 보류, 필요 시 해제 후 바이트 상한 추가.
- Kestrel MaxRequestBodySize로 본문 상한 초과를 인증 이전 413으로 처리.
- raw 보존: KeepRawJsonl 기본 true, RawRetentionDays 90. 기동 시 만료분 삭제(expiredRawDeleted 로그) 확인.

## 9. 검증 계획 (수동, 테스트 코드 작성 금지 규칙 준수)

1. 에디터 Play 종료 → 세션 JSONL 생성 확인 → 서버 CSV 생성 확인.
2. 서버를 끈 상태로 Play 종료 → `.pending` 유지 확인 → 서버 재기동 후 다음 Play 기동 때 재전송 확인.
3. Play 중 강제종료(작업 관리자로 프로세스 종료) → 다음 기동 시 endedCleanly=false로 재전송 확인.
4. 같은 세션 파일 2회 POST → CSV 행 중복 없음(replaced) 확인.
5. 로그 20,000건 초과 유도 → truncated 마커와 상한 동작 확인.
6. Windows 빌드에서 1~3번 재확인.

## 10. 승인 필요 사항

1. 서버 런타임: ASP.NET Core 8 권장. Python(FastAPI) 선호 시 계약 유지한 채 대체 가능 — 선택 필요.
2. 서버 실행 환경: 플레이테스트 PC에서 직접 실행(LAN, HTTP)인지 외부 배포(HTTPS 필요)인지 — `_serverUrl` 기본값과 키 관리가 달라진다.
3. Google Sheets 반영 범위: 세션 요약만(권장) vs 원시 로그 전체 — 권장안은 요약만이다.
4. Sheets 사용 여부와 스프레드시트 준비 주체(사용자가 시트 생성 후 공유 필요).
5. GameLogger를 독립 싱글턴으로 둘지, Managers 서비스로 편입할지 — 권장안은 독립 싱글턴이다.
6. 로그 보존 기간(권장: raw 90일, 요약·CSV 무기한)과 pending 정리 기간(30일) 기본값.
