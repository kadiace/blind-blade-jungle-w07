# Unity 리팩토링 계획 수립 지시문

## 작업 목적과 범위

이 프로젝트는 AI가 생성한 코드의 비중이 높다. 기능을 추가하면서 스크립트와 문서가 복잡해졌고, 작업마다 필요한 컨텍스트가 길어졌다.

현재 프로젝트를 조사한 뒤 리팩토링 계획을 작성하라. 이번 작업은 조사와 계획 수립까지다. 코드, 씬, 프리팹, 에셋, 패키지, 프로젝트 설정을 변경하거나 Git 커밋을 만들지 마라. 계획 문서는 작성해도 된다.

핵심 목표는 기능 하나를 이해하고 수정할 때 읽어야 하는 코드와 문서의 범위를 줄이는 것이다. 기존 플레이 동작과 데이터, 에셋 연결을 보존하고 사람이 직접 수정하기 쉬운 구조를 제안하라.

스크립트 줄 수, 파일 수, 디자인 패턴 적용 개수는 목표가 아니다.

## 1. 조사 방법

- 적용되는 AGENTS.md와 현재 명세를 먼저 확인하라. 오래된 기획, 완료된 작업 기록, 현재 구현을 구분하라.
- 프로젝트 안내와 파일 목록으로 주요 기능을 파악하고, 기능의 진입점부터 관련 코드와 에셋으로 조사 범위를 넓혀라. 처음부터 모든 파일을 읽지 마라.
- 자주 수정하는 기능, 책임이 섞인 클래스, 중복 규칙, 순환 의존, 여러 곳에서 변경하는 상태를 우선 조사하라.
- 코드의 이름이나 주석만으로 의도를 확정하지 마라. 실제 호출부, 데이터 변경 지점, 관련 에셋을 확인하라.
- 문제마다 실제 파일 경로와 클래스·메서드·필드 등 근거를 제시하라. 프로젝트에서 발견하지 않은 문제를 발견한 것처럼 쓰지 마라.
- 확인된 사실, 설계상 추정, 추가 확인이 필요한 항목을 구분하라. 실행하지 않았다면 코드 분석으로 확인한 범위만 설명하라.

전체 개요는 간결하게 작성하고, 실제 변경 후보는 판단에 필요한 깊이까지 조사하라.

## 2. 동작 보존과 기준 상태

리팩토링은 기존 동작을 유지하는 구조 변경으로 계획하라. 기능 추가, 밸런스 변경, 버그 수정, 성능 최적화는 별도 항목으로 분리하라.

대상 기능별로 다음을 정리하라.

- 실행 진입점과 주요 처리 순서
- 입력, 출력, 상태 변경과 변경 시점
- 관련 씬·프리팹·SO 및 인스펙터 설정
- 현재 확인 가능한 정상 동작과 알려진 문제
- 변경 후 동일해야 하는 결과와 이를 확인할 방법

예를 들어 자원 차감, 쿨타임 시작, 피해 적용, 이벤트 발생 시점도 보존 대상이다. 기존 코드와 명세가 다르면 차이를 기록하고 의도한 동작을 임의로 결정하지 마라.

구현 시작 전에 필요한 기준 커밋·브랜치와 검증 상태를 제안하되, 이번 조사에서 직접 생성하거나 변경하지 마라.

## 3. 책임과 의존 관계

각 주요 클래스의 책임, 소유 데이터, 외부 의존, 호출 방향을 파악하라.

- 입력, 게임 규칙, 실행 처리, 표시, 저장 책임이 섞였는지 확인하라.
- 한 기능을 수정할 때 함께 수정해야 하는 범위와 이유를 확인하라.
- 순환 참조와 거대한 Manager를 거치는 의존을 검토하라.
- 중복 코드는 같은 규칙인지 확인한 뒤 통합을 제안하라. 비슷하게 생겼다는 이유만으로 합치지 마라.
- 기능별 폴더와 관련 파일 배치가 탐색에 도움이 되는지 검토하라.

클래스는 책임과 변경 이유를 기준으로 분리하라. 단순히 파일을 짧게 만들기 위한 분리나, 흐름을 추적하기 어렵게 만드는 중간 계층은 피하라.

직접 호출, 이벤트, 인터페이스, FSM, SO, 상속, DI는 구체적인 문제를 해결할 때만 제안하라. 도입할 경우 해결하는 문제와 추가되는 복잡성을 설명하라. 현재 요구에 없는 확장 가능성을 위해 범용 구조를 만들지 마라.

## 4. 상태와 데이터 소유권

중요한 상태마다 원본을 소유하는 곳과 변경 권한을 정리하라.

- 같은 의미의 상태가 여러 시스템에 중복 저장되는지 확인하라.
- 외부 시스템이 상태를 직접 변경하는 지점을 확인하라.
- 설정값, 실행 중 상태, 저장 데이터를 구분하라.
- SO를 공유하는 객체들이 실행 중 값을 의도치 않게 함께 변경하는지 확인하라.
- 여러 bool이나 캐시가 같은 상태를 표현한다면 원본과 갱신 규칙을 확인하라.
- 초기화, 종료, 씬 전환, 재활성화, 풀링 후 재사용 시 상태가 어떻게 정리되는지 확인하라.

권위 있는 원본과 변경 경로를 명확히 하되, 성능이나 독립적인 생명주기 때문에 필요한 복사·캐시는 유지할 수 있다. 제거 여부를 근거와 함께 판단하라.

## 5. Unity 연결과 데이터 이전

C# 호출 관계 외에 Unity 에셋과 설정에서 발생하는 연결을 조사하라.

- 스크립트 이동·이름 변경 시 기존 .meta와 GUID 보존
- 직렬화 필드 이름·타입·선언 위치 변경의 영향
- 컴포넌트 분리 시 인스펙터 값과 참조 이전
- 씬, 프리팹 변형, SO, 기존 저장 데이터의 호환성
- UnityEvent, Animation Event, 문자열 기반 호출, 리플렉션 등 코드 검색만으로 놓칠 수 있는 사용처
- Awake/OnEnable/Start 등 초기화 순서와 이벤트 구독·해제
- 프로젝트에서 사용하는 코루틴·비동기 작업의 종료 및 취소 처리

필드 이름 변경에는 필요한 경우 FormerlySerializedAs를 검토하라. 필드 타입 변경이나 다른 컴포넌트로의 이동까지 해결한다고 가정하지 마라.

이전이 필요한 변경은 대상 에셋, 이전 방법, 검증 방법, 되돌리는 방법을 계획에 포함하라. 참조 검색 결과가 없다는 이유만으로 코드나 에셋을 미사용으로 확정하지 마라.

## 6. AI 생성 코드에서 검토할 항목

다음은 조사 후보이며, 실제 존재 여부와 유지 이유를 확인한 뒤 판단하라.

- 사용하지 않는 범용 클래스·인터페이스
- 이전 구현과 새 구현의 공존
- 같은 기능을 처리하는 중복 실행 경로
- 반복적인 자동 탐색·참조 복구·fallback
- 설정 오류를 숨기는 null 처리나 예외 처리
- 아직 없는 기능을 전제로 만든 추상화
- 실제 구현과 맞지 않는 주석·문서

삭제나 단순화를 제안할 때는 사용처와 필요성을 확인한 근거를 제시하라. 필수 참조 누락은 명확하게 검증하고, 선택적 참조나 정상적인 예외 상황은 기존 요구를 유지하라.

성능 개선이 필요하다고 판단하면 측정 근거나 필요한 측정 방법을 제시하라. 코드가 길거나 GetComponent, 이벤트 등을 사용한다는 이유만으로 성능 문제를 단정하지 마라.

## 7. 컨텍스트와 문서 정리

에이전트가 매 작업마다 전체 프로젝트와 과거 작업 기록을 읽지 않아도 되도록 문서 구조를 제안하라.

- AGENTS.md: 공통 작업 규칙과 필수 검증
- 프로젝트 안내: 기능 위치와 관련 문서 링크
- 기능별 문서: 책임, 진입점, 상태 소유자, 의존 관계, 관련 에셋, 검증 방법
- 현재 작업 명세: 이번 변경 범위와 완료 조건

문서에 코드 내용을 그대로 반복하지 마라. 코드만으로 알기 어려운 의도와 제약, 어디부터 읽어야 하는지를 남겨라.

중복 규칙은 기준 문서를 정하고 링크로 연결하라. 폐기한 설계와 완료된 기록은 현재 명세와 구분하라. 기존 문서를 조사한 뒤 필요한 변경만 제안하고, 새로운 문서를 무조건 늘리지 마라.

## 8. 단계와 검증

전체를 한 번에 재작성하지 마라. 기능 또는 책임 단위로 작게 나누고, 각 단계가 검증 가능한 상태로 끝나도록 계획하라.

단계마다 다음을 포함하라.

- 해결할 문제와 우선순위
- 수정 대상 파일·에셋과 영향 범위
- 변경 전후의 책임·상태·호출 관계
- 보존할 동작과 변경하지 않을 범위
- 데이터 이전 및 필요한 선행 단계
- 검증 방법, 완료 조건, 되돌리는 방법

우선순위는 수정 빈도, 문제의 영향, 기대 효과, 변경 위험, 검증 가능성을 함께 고려하라. 공통 핵심 시스템을 무조건 먼저 고치거나, 가장 긴 파일부터 고치지 마라.

검증은 변경의 위험에 맞춰 선택하라.

- 순수 계산과 게임 규칙: 의미 있는 자동 테스트
- 입력·씬·프리팹·애니메이션 연결: Play Mode 또는 수동 플레이
- 생명주기 변경: 재활성화·씬 재진입·재사용 등 해당 시나리오
- 주요 단계 완료: 대상 플랫폼 빌드와 핵심 흐름 확인

실제 회귀를 잡을 수 있는 검증을 우선하라. 동일한 검증을 불필요하게 반복하거나 구현을 그대로 따라 하는 테스트를 늘리지 마라. 자동 확인이 어려운 항목은 사용자가 실행할 절차와 예상 결과를 적어라.

## 요청하는 계획 출력

다음 순서로 Markdown 계획을 작성하라.

1. 현재 구조와 복잡성이 생긴 주요 원인
2. 근거가 있는 문제 목록: 위치, 문제, 영향, 우선순위
3. 제안 구조: 책임, 의존 방향, 상태 소유권과 기존 구조와의 차이
4. 단계별 변경 계획: 대상, 보존 조건, 이전, 검증, 완료 조건, 되돌리기
5. 컨텍스트·문서 정리 계획
6. 지금 유지할 구조와 리팩토링에서 제외할 항목
7. 확인하지 못한 사항과 사용자 판단이 필요한 질문

검증하지 않은 사항은 확인했다고 쓰지 마라. 작업 시간이나 컨텍스트 절감량을 근거 없이 수치화하지 마라.

추가 질문이 필요해도 먼저 독립적으로 조사할 수 있는 범위와 계획을 완성하라. 동작 의도나 데이터 호환성처럼 사용자의 답에 따라 설계가 달라지는 질문만 남겨라.

계획의 성공 기준은 수정 시 읽고 고칠 범위가 줄고, 상태 변경 경로를 찾기 쉬워지며, 기존 동작과 Unity 연결을 보존하고, 사람이 핵심 실행 흐름을 설명할 수 있는 것이다.
